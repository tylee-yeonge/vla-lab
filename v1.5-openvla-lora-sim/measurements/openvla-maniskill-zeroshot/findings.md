## 1. 측정 장치를 먼저 검증했다

### 1.1 왜 순서를 이렇게 잡았는가

zero-shot 성공률이 0 으로 나오면 원인이 두 갈래다.

1. 모델이 이 화면·이 로봇을 처음 봐서 못 한다 (도메인 갭)
2. 내가 만든 환경·루프·판정·변환이 고장났다

**두 원인이 똑같은 숫자를 만든다.** 그래서 숫자를 먼저 재면 그 숫자를 해석할 수 없다. 측정 전에 "장치는 정상이다"를 따로 증명해야 하고, 방법은 **정답을 아는 해법을 같은 장치에 넣어 보는 것**이다. 정답을 아는 해법이 실패하면 그것은 해법 탓이 아니라 장치 탓이다.

결과는 [`methodology.md`](methodology.md) §7.1 - §7.2 에 있다. 상한 20/20, 하한 1/20.

**상한 20/20 이 뜻하는 것**: 같은 환경 설정·같은 루프 구조·같은 성공 판정·같은 정규화 action 경로에서 성공이 실제로 집계된다. 즉 이 측정에서 0 이 나와도 그것을 "장치 고장"이 아니라 "정책의 성적"으로 읽을 수 있다.

**step 예산 판정**: 정답을 아는 해법이 최대 49 step 으로 끝났고 예산은 200 이다. 약 4배 여유가 있으므로 **실패를 step 예산 부족으로 설명할 수 없다.** 이 비교가 없으면 "시간이 부족했나" 라는 가설을 배제할 수 없다.

**하한 1/20 이 뜻하는 것**: seed 8 의 성공은 조작 능력의 증거가 아니다. 성공률을 보고할 때 이 하한을 함께 적고, 해석 단계에서 걷어낸다. 이 값을 모르면 정책의 성과와 초기 배치 운을 구분할 수 없고, 같은 혼동이 이후 fine-tuned 측정과의 before/after 비교에서 반복된다.

### 1.2 motion planning 을 쓰지 않은 판단

상한 대조에는 ManiSkill 내장 motion planning 해법을 쓰려 했으나 실행 자체가 불가능했다 (원인·증거는 [`methodology.md`](methodology.md) §7.1). `mplib` 바이너리가 numpy 1.x C API 로 빌드돼 있어 설치된 numpy 2.x 와 ABI 가 맞지 않고, 파이썬 예외가 아니라 세그폴트로 죽는다.

우회로 두 개를 검토했다.

| 선택지 | 판단 | 사유 |
|---|---|---|
| numpy 를 1.26.4 로 내린다 | 비채택 | mplib 은 살지만 `scipy` / `opencv-python` 이 numpy>=2 를 요구해 그쪽이 깨진다. 측정 환경 전체를 흔든다 |
| scripted 정책을 직접 쓴다 | **채택** | 본 측정과 같은 `control_mode` 를 쓰므로 검증 범위가 오히려 넓다 (motion planning 은 `pd_joint_pos` 라 정규화 action 경로를 지나가지 않는다) |

대가: scripted 정책은 공식 기성 해법이 아니라 이 검증을 위해 직접 작성한 코드다. 20/20 은 "좌표를 아는 정책이면 이 장치에서 성공이 집계된다"의 증거이지, ManiSkill 공식 성능 수치가 아니다.

### 1.3 이 검증이 배제한 용의자

| 용의자 | 배제됐나 | 근거 |
|---|---|---|
| 환경 설정 (`obs_mode` / `control_mode` / 카메라) | 배제 | 같은 설정에서 20/20 |
| episode 루프 (reset, step, 종료 조건) | 배제 | 같은 루프 구조로 성공이 집계됨 |
| 성공 판정 정의 | 배제 | 성공을 실제로 감지했다. 도달 불가능한 조건이 아니다 |
| step 예산 200 | 배제 | 최대 49 step 으로 충분 |
| `[-1, 1]` 정규화 action 이 물리량으로 풀리는 경로 | 배제 | scripted 해법이 이 경로로 팔을 정확히 움직였다 |
| 부분 도달률 판정식 (`reached` / `lifted`) | 배제 | 음성·양성 대조를 직접 확인 ([`methodology.md`](methodology.md) §3.2) |
| OpenVLA 출력을 번역하는 변환 레이어 | **부분** | scripted 해법은 이 함수를 지나가지 않는다. gripper 규약만 §2.2 에서 별도로 확인됨 |
| 시각 입력 경로 (모델이 받는 이미지가 장면을 담고 있는가) | **부분** | 렌더 자체는 [`raw/env_check.png`](raw/env_check.png) 로 확인. 그 이미지가 정책에 전달되는 경로는 예외 없이 통과했다는 것 외에 내용 검증을 하지 않았다 |

## 2. 변환 레이어에서 잡은 오류와 대응

### 2.1 무증상으로 틀리는 오류 하나를 실제로 만들었다

첫 실행은 모델 출력을 변환 없이 그대로 환경에 넣었다. **예외가 나지 않았고, 출력 형태도 정상이었다.** OpenVLA 의 물리량 출력이 우연히 `[-1, 1]` 안에 들어오기 때문에 `env.step` 이 값을 그대로 받아들인다.

| 항목 | 변환 생략 시 실제 거동 | 출처 |
|---|---|---|
| 위치 명령 | 의도의 **1/10.3** (정책 1회당 0.0088 m vs 0.0910 m) | [`methodology.md`](methodology.md) §4.1 실측 |
| 회전 | 부호 반전 + 1/10 스케일 | 계약 표 4번 미적용 |
| gripper "닫힘" 명령 | finger 관절이 0.015 m 에 머문다 (완전 닫힘 0.0 에 못 미침) | §4.1 실측 |

그 실행의 출력은 `placed 1/20`(= 하한 seed) 이었고 나머지 단계는 전부 0 이었다. **수정 후 재실행의 결과와 숫자가 같다** ([`methodology.md`](methodology.md) §6.1). 즉 이 오류는 결과 숫자로는 드러나지 않았고, 코드를 읽어야 드러났다.

여기서 얻은 규칙: **0% 는 자기 진단을 하지 않는다.** 배선이 끊겨도 0, 모델이 못 해도 0 이다. 그래서 §1 의 상한·하한 대조와 아래 §2.2 의 규약 확인이 숫자보다 먼저 필요하다.

같은 실행에서 부분 도달률 3단계는 판정식이 구현되지 않은 상태였고, 요약 출력은 그것을 `0/20` 으로 찍었다. 미구현 상수가 측정값처럼 보이는 형태였다. 대응: 판정식을 구현하고 음성·양성 대조를 붙였다 ([`methodology.md`](methodology.md) §3.2).

### 2.2 gripper 규약은 실측으로 확인됐다

계약 표 5번의 `[0, 1]`, `0 = 닫힘` 은 코드에서 읽은 값이 아니라 학습 파이프라인에서 추론한 값이었다. 측정 중 `raw_action[6]` 951개를 전량 기록해 확인했다 ([`methodology.md`](methodology.md) §6.3).

| 확인 사항 | 결과 |
|---|---|
| 나타난 서로 다른 값 | 2개뿐 (`0.0` 658회, `0.9961` 293회) |
| 중간값 (0.1 - 0.9) | 0회 |
| 음수 | 0회 |

이산 이진 규약이라는 가정이 맞았고, `-1` 근처 값이 나오지 않았으므로 `g = 2*raw - 1` 변환 규칙을 그대로 유지한다. 이 항목은 계약 표에서 유일하게 추론으로 남아 있던 행이었고, 이제 실측 근거가 붙었다.

## 3. 성공률·부분 도달률 해석 (본인 작성 영역 — 작성 대기)

이 절은 대신 작성하지 않는다. 아래 질문에 답하는 형태로 본인 문장으로 채운다. 수치는 [`methodology.md`](methodology.md) §6 에 있다.

**3.1 `placed` 를 어떻게 보고할 것인가**

- 원시 값은 `1/20` 이고 하한을 걷어낸 값은 `0/20` 이다. 대외 보고에 어느 쪽을 쓰고, 다른 쪽은 어떻게 병기할 것인가
- 이후 fine-tuned 측정과 비교할 때 하한 seed 를 어떻게 다룰 것인가 (같은 목록 유지 / 제외 / 별도 집계)

**3.2 `reached` 가 0/20 인 것을 어떻게 읽을 것인가**

- 상한 대조는 통과했고 step 예산도 4배 여유가 있다 (§1.1). 그렇다면 팔이 큐브 5 cm 안에 한 번도 들어가지 못한 것은 무엇을 뜻하는가
- 정책이 "아무 방향으로도 움직이지 않았다"와 "일관되게 엉뚱한 방향으로 움직였다"를 이 데이터로 구분할 수 있는가. 구분할 수 없다면 무엇을 더 기록해야 하는가
- 부분 도달률을 넣은 목적은 최종 성공률이 0 일 때 신호를 보는 것이었다. 그 목적이 이번에 달성됐는가

**3.3 남은 두 가설 중 어디에 무게를 둘 것인가**

- 도메인 갭 (embodiment·카메라 시점·명령 문장이 학습 분포와 다르다)
- 변환 레이어의 잔여 버그 (gripper 외 항목은 §1.3 에서 부분 배제 상태)
- 두 가설을 가르기 위해 다음에 무엇을 재야 하는가. §4 의 미확인 항목 중 어느 것이 이 판단에 직접 걸리는가

**3.4 이 값을 before 로 쓸 수 있는가**

- 모든 단계가 0 인 before 값으로 after 와의 차이를 보일 수 있는가. 보일 수 없다면 baseline 정의(임계값·해상도·명령 문장) 중 무엇을 바꿔야 하는가
- 바꾸면 이 측정과의 비교 가능성이 사라진다. 그 대가를 감수할 것인가

## 4. 이 측정이 확정하지 못한 것

- **공개 수치 대조 미실시.** 같은 조합의 외부 보고 수치와 맞춰 보지 않았으므로, §3.3 의 두 가설을 데이터로 가르지 못한다.
- **변환 레이어 전체 검증 미완.** gripper 규약(§2.2)만 실측으로 확인됐다. 위치·회전 변환은 컨트롤러 사상 실측([`methodology.md`](methodology.md) §4.1)까지만이고, 모델 출력이 그 규약대로 해석되는지는 별도 증거가 없다.
- **`bridge_orig` 의 5 Hz 미확인.** action repeat 4 의 전제이며 데이터셋 카드로 확인해야 한다.
- **단일 시점·단일 문장.** 카메라 시점과 명령 문장을 각각 하나만 썼으므로 민감도를 모른다.
- **numpy 버전 기록 불일치.** [`environment.md`](environment.md) §6 참조. 재현 시 첫 확인 대상이다.
